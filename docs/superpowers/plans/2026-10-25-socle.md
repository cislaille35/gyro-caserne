# Socle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Poser le socle de Gyro Caserne : les personnes, les profils, les droits, les responsabilités, les comités, les attributions datées et la vérification de droit unique, ainsi que la connexion par lien magique réservée aux adresses autorisées.

**Architecture:** Un nouveau paquet `packages/socle` porte le schéma Drizzle, les migrations SQL, les listes fermées, la vérification `aLeDroit` et les actions protégées. Il ne dépend pas de Cloudflare : ses tests tournent sur `node:sqlite` en mémoire, branché à Drizzle par `drizzle-orm/sqlite-proxy`. En production, `apps/web` branche le même code sur D1 (`drizzle-orm/d1`). Better Auth gère la connexion par lien magique et Resend envoie les e-mails.

**Tech Stack:** TypeScript 6, Drizzle ORM 0.45.4 + drizzle-kit 0.31.11, Cloudflare D1, Better Auth 1.7.12 (plugin `magicLink`), Resend 6.34.1, Vitest 5, Node 24 (`node:sqlite`).

**Spec:** `docs/superpowers/specs/2026-10-25-modele-metier-design.md`, avec `docs/fonctionnel/acces-et-attributions.md` et `docs/fonctionnel/fiche-agent.md`.

## Global Constraints

- Français partout : noms de tables, de colonnes, de fonctions, commentaires et messages (`CLAUDE.md`).
- Versions exactes (`saveExact`) ; chaque dépendance ajoutée est justifiée dans la PR et reportée dans `docs/technique/README.md`.
- Rien de propre à un centre dans le code : les équipes viennent de `centres/<id>/centre.ts` (jeu de départ), et le reste du jeu de départ est commun.
- Aucun secret dans le dépôt : `BETTER_AUTH_SECRET`, `SUPER_ADMINS`, `RESEND_CLE` et `COURRIEL_EXPEDITEUR` sont des secrets Cloudflare (en local, `apps/web/.dev.vars`, ignoré par git ; un `.dev.vars.exemple` montre les noms).
- Une **liste fermée** est définie une seule fois en TypeScript, et la base la reprend dans une contrainte `CHECK` générée à partir de ce même tableau.
- **Dates** : texte `AAAA-MM-JJ`. Une attribution ou une affectation est **en cours** à la date `d` si `debut <= d` et (`fin` est nul ou `d <= fin`). La fin est incluse.
- **Adresses e-mail** : toujours enregistrées et comparées en minuscules, sans espaces autour.
- D1 n'a pas de transaction interactive : une action qui écrit plusieurs lignes (dont le journal) utilise `base.batch([...])`.
- Pas d'écran soigné : les pages de connexion sont nues. Le design se discute avant les premiers vrais écrans.

## Review Focus

1. Une adresse saisie « ` Dupont@Exemple.FR ` » doit être reconnue comme `dupont@exemple.fr`, à l'ajout comme à la connexion (tests : Tâche 3 et Tâche 8).
2. Une attribution dont la fin est aujourd'hui est encore valable aujourd'hui, et celle qui commence demain ne l'est pas encore (Tâche 5).
3. Un agent suspendu ou parti n'a plus aucun droit, même s'il garde une attribution en cours, par exemple chef de centre (Tâche 5), et il ne peut plus recevoir de lien de connexion (Tâche 8).
4. Un chef d'équipe qui a `GERER_ACCES` sur l'équipe 2 ne peut pas ajouter quelqu'un à l'équipe 3, ni ajouter une personne au profil extérieur (Tâche 6).
5. Charger deux fois le jeu de départ ne crée aucun doublon (Tâche 7).

### Task 5 : La vérification unique `aLeDroit`

**Files:**
- Create: `packages/socle/src/droits.ts`, `test/droits.test.ts`

**Interfaces:**
- `type Acteur = { type: 'super'; email: string } | { type: 'personne'; id: number }`
- `type Perimetre = { type: 'centre' } | { type: Exclude<TypePerimetre, 'centre'>; id: number }`
- `couvre(detenu: Perimetre, vise: Perimetre): boolean` : le centre couvre tout, sinon même type et même id.
- `aLeDroit(base: Base, acteur: Acteur, droit: Droit, vise: Perimetre, date: string): Promise<boolean>` :
  1. un super administrateur a tous les droits ;
  2. une personne dont le statut n'est pas dans `STATUTS_AVEC_ACCES` n'en a aucun ;
  3. sinon, le droit vient d'un `profil_droit` de son profil dont le périmètre couvre `vise`, **ou** d'une attribution en cours à `date` dont la responsabilité porte ce droit et dont le périmètre couvre `vise`.
- `droitsDe(base, acteur, date): Promise<Array<{ droit: Droit; perimetre: Perimetre }>>` : la même logique, pour l'affichage. `aLeDroit` s'appuie dessus, pour que la règle n'existe qu'à un seul endroit.

- [ ] **Step 1 : tests qui échouent**, avec un petit jeu de données (un profil agent qui a `VOIR_PLANNING` sur le centre, une responsabilité « Chef d'équipe » qui a `VALIDER_REMPLACEMENT`, les équipes 1 et 2) :
  - `it('le super administrateur a tous les droits')`
  - `it('donne un droit du profil')` : `VOIR_PLANNING` sur le centre → `true`
  - `it('un droit sur le centre couvre une équipe')` : `VOIR_PLANNING` sur l'équipe 2 → `true`
  - `it('un droit sur une équipe ne couvre pas une autre équipe')` : chef de l'équipe 1, `VALIDER_REMPLACEMENT` sur l'équipe 2 → `false`
  - `it('une attribution qui finit aujourd’hui vaut encore aujourd’hui')` et `it('une attribution qui commence demain ne vaut pas encore')`
  - `it('un agent suspendu n’a plus aucun droit')` : agent avec un statut `suspendu` et une attribution chef de centre en cours → `false`
  - `it('une personne extérieure n’a que les droits de son profil')`
- [ ] **Step 2 / 3 / 4** : échec, implémentation, succès.

### Task 6 : Actions protégées

**Files:**
- Create: `packages/socle/src/erreurs.ts`, `src/actions/personnes.ts`, `src/actions/attributions.ts`, `test/actions-personnes.test.ts`, `test/actions-attributions.test.ts`

**Interfaces:**
- `class RefusDroit extends Error` (avec `droit` et `perimetre`) et `class DonneeInvalide extends Error`.
- Chaque action vérifie d'abord ses droits avec `aLeDroit`, puis écrit ses lignes et `ligneJournal` dans un même `base.batch`. Toutes prennent `aujourdhui: string`.
- `ajouterPersonne(base, acteur, donnees: { email; prenom; nom; profilId; equipeId?: number }, aujourdhui): Promise<number>` :
  - l'adresse est normalisée ;
  - il faut `GERER_ACCES` sur le centre, **ou** sur `equipe:equipeId` si le profil est de type `agent` ;
  - avec `equipeId`, une affectation commençant `aujourdhui` est créée.
- `changerStatut(base, acteur, personneId, statut: StatutOperationnel, aujourdhui)` : il faut `GERER_ACCES` sur le centre ou sur l'équipe en cours de la personne.
- `affecterEquipe(base, acteur, personneId, equipeId, debut)` : clôt l'affectation en cours la veille de `debut`. Il faut `GERER_ACCES` sur le centre.
- `attribuer(base, acteur, a: { personneId; responsabiliteId; perimetre: Perimetre; debut; fin?: string; compteRendu?: string }, aujourdhui): Promise<number>` :
  - `perimetre.type` doit être le `type_perimetre` de la responsabilité, sinon `DonneeInvalide` ;
  - la responsabilité système `chef_centre` ne peut être attribuée que par un super administrateur ;
  - sinon, il faut `ATTRIBUER_RESPONSABILITE` sur `comite:comite_attributeur_id`, ou sur le comité visé si l'attributeur est nul (règle de la Tâche 4).
- `finirAttribution(base, acteur, attributionId, fin, aujourdhui)` : mêmes droits que `attribuer`.
- `modifierDroitsResponsabilite(base, acteur, responsabiliteId, droits: Droit[], aujourdhui)` : il faut `GERER_LISTES` sur le centre. Retirer un droit `verrouille` lève `DonneeInvalide`.

- [ ] **Step 1 : tests qui échouent**
  - `it('normalise l’adresse ajoutée')` : `' Dupont@Exemple.FR '` est enregistrée `dupont@exemple.fr`.
  - `it('un chef d’équipe ajoute un agent à son équipe')` (succès) ; `it('… mais pas à une autre équipe')` → `RefusDroit` ; `it('… ni une personne extérieure')` → `RefusDroit`.
  - `it('seul le super administrateur nomme le chef de centre')`.
  - `it('le rapporteur de l’amicale ne peut pas nommer un chef d’équipe')` → `RefusDroit`.
  - `it('refuse un périmètre qui ne correspond pas à la responsabilité')` → `DonneeInvalide`.
  - `it('refuse de retirer un droit verrouillé')` → `DonneeInvalide`.
  - `it('chaque action écrit une ligne de journal')`.
- [ ] **Step 2 / 3 / 4** : échec, implémentation, succès.
- [ ] **Step 5** : commit `Socle : actions protégées et journal`.
